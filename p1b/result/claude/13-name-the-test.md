**Budget reconciliation (three lines).** Core M0 is F0+T1+T2+T5 = **24 h** against N4's 18 h, so N4 is under-costed by 6 h before anything else is built. The full 61 h of test-build sits inside N2+N3+N4+N5a (74 h combined), leaving 13 h for implementation in those milestones — that does not close, and it is a stronger reason to drop N5b (8.75 h) than the 5% margin already given. Cut order if it still does not close: T12 (3 h) and T13 (2 h) are process, not product; T7 (3 h) is partly subsumed by T3; that buys 8 h and nothing below that line can be cut without deleting a claim.

**How M0 will be evaluated, and what would make it fail.** M0 is run entirely offline against a frozen corpus committed to the repository — the 50 recipes and 528 recipe-ingredient rows in `backend/dataset/`, joined to ten seeded pantries in `web/tests/p2/fixtures/pantries/` with the clock pinned to 2026-10-01 — producing 50 × 10 = 500 recommendations per invocation, with one prior run against the live `gemini-2.5-flash` endpoint (30 calls, archived as JSON) supplying the baseline so that no marker ever has to re-run it or hold an API key. Three numbers decide it: the displayed total equals the sum of the displayed line items in 500/500 cases; the SHA-256 digest of the ranked list is identical across 20 committed permutations of each pantry's input order; and the fraction of the 500 rankings whose top-5 order changes after one flagged line is corrected lands inside a band, 0.20 to 0.95, that is pre-registered in N1 before the scorer is written. The first two are the invariants a marker will call trivial, and the honest answer is that they are trivial **and today's build does not have them** — the baseline is not zero-by-definition but a measured disagreement rate X between three repeat runs over identical pantries, because `RecommendedRecipe.match_score` at `inventory_recommender.py:50` is authored by the model, so two runs have no reason to agree; T4's baseline is likewise measured, being the count of ingredient names the model emitted that match no row in the 448-name catalog. M0 fails if any one of these breaks: the total is clamped or rounded for display without booking the adjustment as its own line item, so the arithmetic invariant is a lie about what the user sees; ties are left to sort stability rather than broken on `recipe_id`, so permuting the pantry permutes the output and the digest test collapses; a line item names an ingredient with no resolvable `inventory_row_id`, which means the receipt cannot be pointed at; or — the only outcome we cannot engineer around — the correctability fraction falls below 0.20, which would mean we built a receipt that is printed beside the ranking rather than one the ranking is computed from, and we would have to report that number as it came out.
