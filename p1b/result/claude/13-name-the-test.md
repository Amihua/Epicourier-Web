**How M0 will be evaluated, and what would make it fail.** M0 is run entirely offline against a frozen corpus committed to the repository — the 50 recipes and 528 recipe-ingredient rows in `backend/dataset/`, joined to ten seeded pantries in `web/tests/p2/fixtures/pantries/` with the clock pinned to 2026-10-01 — producing 50 × 10 = 500 recommendations per invocation, with one prior run against the live `gemini-2.5-flash` endpoint (30 calls, archived as JSON) supplying the baseline so that no marker ever has to re-run it or hold an API key. Three numbers decide it: the displayed total equals the sum of the displayed line items in 500/500 cases; the SHA-256 digest of the ranked list is identical across 20 committed permutations of each pantry's input order; and the fraction of the 500 rankings whose top-5 order changes after one flagged line is corrected is **reported as it comes out, to 2 dp, with no threshold**. *(⚠ Corrected 2026-09-13: this sentence previously required that fraction to land inside a band of 0.20 to 0.95. **That band had no derivation anywhere in this file** — see T5. It is withdrawn, and what is pre-registered in N1 before the scorer is written is the correction rule, the statistic, and the promise to publish the number unedited. Only two of the three numbers now decide pass/fail; the third is a measurement we commit to publishing.)* The first two are the invariants a marker will call trivial, and the honest answer is that they are trivial **and today's build does not have them** — the baseline is not zero-by-definition but a measured disagreement rate X between three repeat runs over identical pantries, because `RecommendedRecipe.match_score` at `inventory_recommender.py:50` is authored by the model, so two runs have no reason to agree; T4's baseline is likewise measured, being the count of ingredient names the model emitted that match no row in the 448-name catalog — **though the matching rule itself is not yet pre-registered and must be committed as code in N1 before the archive is opened (see T4), so that count cannot be quoted today.** M0 fails if any one of these breaks: the total is clamped or rounded for display without booking the adjustment as its own line item, so the arithmetic invariant is a lie about what the user sees; ties are left to sort stability rather than broken on `recipe_id`, so permuting the pantry permutes the output and the digest test collapses; a line item names an ingredient with no resolvable `inventory_row_id`, which means the receipt cannot be pointed at; or a line item names an ingredient the pre-registered normaliser cannot resolve. **The one outcome we cannot engineer around is unchanged and is now stated without a fabricated cutoff:** the correctability fraction comes out low enough that the receipt is evidently printed *beside* the ranking rather than being the thing the ranking is computed from — and we report that number as it came out, whatever it is, because we have no derived threshold to hide behind and are not inventing one.
