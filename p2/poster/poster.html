Mission — why / what / so what

Why. Epicourier already recommends recipes from your pantry, and the match percentage it prints in bold is written by a language model. No line of our code computes it. The response schema has no field that could hold a per-ingredient contribution, so 0 of 300 returned scores can be broken down — not an estimate, a property of the schema. A user who disagrees has nothing to point at, and the team cannot tell whether a change improved the ranking or merely moved it.

What. We replaced the number with a receipt: ranking computed by a pure function against a published table and printed as lines that add up to the total — each naming the pantry item, its date, and the points it contributed. Correct any line and the order moves. The model keeps the sentence it is good at and loses the authority to invent the score.

So what. The ranking became measurable, so it became improvable — each claim stated as a threshold before the code existed, and each met.

  • M1 · deterministic scoring. Pure function — no model, no clock; expired stock unusable, zero stays zero.
  • M2 · receipt panel. Every line visible and correctable; edits persist and re-rank.
  • M3 · pantry delta. missing = max(required − usable, 0); preview writes nothing, confirm is idempotent in the database.

  • Per-purchase lots. The schema sums per location, so "which batch" cannot be answered. Add the table, migrate.
  • Verification gate. Check every ingredient an explanation asserts against the 448-row catalogue.
  • Does it change behaviour? A within-subject study. Labelled a hypothesis, not a need.

What this output is claiming. The expectations were written by hand from the frozen contract before any scorer existed; the scorer was then written independently against the same contract. They agree on every value — three totals, nine subtotals, fifteen receipt lines. Two independent derivations matching is evidence; a function compared with itself is not, which is why a deliberately corrupted case is checked first and CI fails if the suite ever accepts it.
What works today — what a Project 3 team inherits on day one
  • A receipt that adds up — line points sum to the total on all 500 cells.
  • A frozen four-module contract — schema, TypeScript and Pydantic, tests fail on drift.
  • An evaluation watched failing — a corrupted case CI is required to reject.
  • Correctable inventory — edits persist, re-rank, and relocation changes nothing.

Why inherit this one: the scoring core is a pure Python function with no network, no key and no clock — run the whole evaluation on a fresh clone in one command, before installing anything. The contract between the four modules is frozen in JSON Schema with additionalProperties:false, so a change that breaks another module fails a test instead of surprising you in week three.
